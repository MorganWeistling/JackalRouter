# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]
- Added: **fast relay**, a local SOCKS5 handshake accelerator (`FastRelay` in `server.py`, `127.0.0.1:7894`). sing-box's SOCKS5 client waits for a reply at every step (`sing/protocol/socks/handshake.go`): TCP, greeting, login, CONNECT, i.e. 4 RTT to the upstream before the first client byte leaves. TCP traffic, including the `proxy-dns` resolver, now goes to the relay instead. sing-box completes those steps over loopback instantly, and the relay sends greeting + login + CONNECT + the client's first bytes (usually the TLS ClientHello) to the upstream as **one packet**, which leaves the TCP handshake plus one exchange. Measured on the live box (RTT to proxy ~98 ms, 8 domains, temporary sing-box instances side by side), medians:

  | Domain state | Old: ready TLS | New: ready TLS | Old: first response byte | New: first response byte |
  |---|---|---|---|---|
  | New domain | 778 ms | 432 ms | 989 ms | 615 ms |
  | Cached domain | 612 ms | 283 ms | 788 ms | 465 ms |

  Throughput is unchanged (2 MB: 1234 vs 1492 KB/s).
  - The relay confirms CONNECT to sing-box before the upstream answers. If the upstream then refuses, the client gets a RST instead of a SOCKS error code. sing-box's TProxy inbound already behaves this way.
  - CONNECT only. UDP ASSOCIATE (QUIC, STUN) stays on the plain `proxy` outbound via a `network: udp` route rule; verified that STUN still reports the proxy's IP.
  - The upstream (address, login, `routing_mark`) is read from the `proxy` outbound of the current `config.json` and reloaded when that file changes, so `/set_proxy` needs no process restart. `proxy` stays first and keeps the real upstream, so `read_active_proxy`, `/status`, `update.py` and local config patches are unaffected. A domain upstream is resolved directly with the system resolver, as sing-box already does via `direct-dns`.
  - The relay runs in its own thread and event loop, because several FastAPI endpoints block for seconds and would otherwise freeze traffic.
- Added: `probe_socks_pipelining()`, which decides whether the relay is used. It sends the one-packet handshake with a real TLS ClientHello to `8.8.8.8:443` and requires the TLS handshake to complete, with full certificate validation. A naive SOCKS5 server that reads each step into a fresh buffer drops the bytes sent after CONNECT and fails the probe; such proxies keep sing-box's own handshake. The probe runs in parallel with the other probes in `probe_proxy()`. `write_singbox_conf(fast_relay=None)` runs the probe itself, so the regeneration code in `update.py` and in the *previous* version's `/self_update` enables the relay without knowing about it. `/set_quic` keeps whatever is in `config.json`, as it already does for the resolver transport.
- Fixed (found while testing the relay): `jackalrouter` ran with systemd's default soft limit of **1024** file descriptors (verified on the box: 1024/524288). With two descriptors per relayed connection, that caps a whole network at ~500 concurrent TCP connections before `Too many open files`. The process now raises its soft limit to `min(hard, 65536)` at startup, which needs no privileges and reaches already-deployed boxes through Update. `LimitNOFILE=65536` was also added to `jackalrouter.service` for new deployments.
- `/status` gains `fast_relay`: `enabled` (the relay is in the config), `listening`, and the counters `active`, `total`, `failed` and `early_data`. `/set_proxy` returns `fast_relay`.
- Verified:
  - 16/16 relay tests against a fake upstream, locally and on the box's Python 3.8: one-packet handshake bytes, 8 MB bidirectional integrity, server-speaks-first protocols (~35 ms extra), half-close, local auth rejection, UDP ASSOCIATE → code 7, upstream refusal → RST and `failed++`, upstream change picked up from config (including a domain upstream), 300 parallel connections, and probe results for a normal, a naive and a refusing upstream.
  - Generated configs, with and without the relay and with or without auth, pass `sing-box check` v1.13.13.
- Changed: `probe_proxy()` now prefers **DoH** over plain `:53` for `proxy-dns`, purely for latency. sing-box's `tcp` DNS transport dials a fresh connection for every query (`dns/transport/tcp.go`, v1.13.13), so each uncached lookup paid a full SOCKS5 handshake through the upstream (~5 RTT), and the `"action": "resolve"` rule runs a lookup before *every* new connection. The `https` transport keeps its HTTP/2 connection alive, so a warm lookup costs ~1 RTT. Order is now DoH `8.8.8.8` → `:53` `8.8.8.8` → DoH `1.1.1.1`; the resolver stays Google wherever possible, so DNS leak tests read the same as before. No new leak surface: both transports go through `detour: proxy` to an IP literal, the no-direct-fallback rule is unchanged, and DoH additionally hides queried domains from the proxy provider.
- Added: `tcp_fast_open` on the SOCKS5 outbound. The SOCKS5 greeting (auth methods only — credentials still go in the next step) rides in the SYN, saving 1 RTT per new connection, including DNS lookups through `proxy-dns`. Effective only if the upstream has TFO enabled; otherwise the kernel silently does a normal handshake, since data is never put in a SYN without a cookie from that server. Check on the box with `nstat -az | grep TCPFastOpenActive`.
- Existing boxes pick both up on the next Route or `/self_update` (both re-probe and regenerate the config). `/set_quic` keeps the resolver transport already in `config.json`. Verified: generated configs for DoH and `:53`, with the proxy given as an IP or as a domain, pass `sing-box check` on v1.13.13 (which rejects unknown fields, so `tcp_fast_open` is really accepted). The new priority order was checked against every probe outcome.

## [1.14.0] - 2026-09-11
- Fixed: proxies from residential gateways (verified on nsocks.com) made every device hang with "sites won't load". The upstream rejects `CONNECT` to **any** address on port 53 and 853 with SOCKS reply code 2 (`not allowed by ruleset`) — standard anti-abuse against DNS tunnelling — while 80/443 stay open. Since `proxy-dns` was plain DNS-over-TCP to `8.8.8.8` and backs `dns.final`, `route.default_domain_resolver` *and* the per-connection `"action": "resolve"` rule, nothing could be resolved at all: `dns: lookup failed … socks5: request rejected, code=2`. Everything else about those proxies is healthy (sticky session, 10/10 parallel connections, ~380 KB/s), so this was purely a transport mismatch on our side.
- Added: `probe_proxy()` — the upstream's capabilities are probed once, in parallel, when a proxy is applied, and the config is generated to match. `proxy-dns` now switches to **DoH** (RFC 8484, HTTP/2 over TCP) when plain `:53` is refused. Plain `:53` keeps priority whenever it works, so the generated config for every proxy that works today is byte-for-byte unchanged. The DoH resolver is addressed by IP literal (`8.8.8.8`, falling back to `1.1.1.1`), so no bootstrap lookup is needed and certificate validation stays fully on — both addresses are in their certificates' IP SANs. `h3` is deliberately not used, as QUIC may be blocked or unsupported by the same upstream.
- Note: there is no fallback to resolving over the box's own WAN. If neither transport is reachable the box stays on `:53` and logs a warning — a broken proxy is preferable to a DNS leak through the real IP, which is the whole point of the project.
- Fixed: the "Block QUIC" checkbox could flip back on its own. `/status` derived it from the presence of the QUIC block rule, but that rule also appears automatically for proxies without UDP ASSOCIATE, so an automatic block was reported back as the operator's choice. The preference is now stored separately in `/var/lib/sing-box/jackal_state.json` (it cannot be derived from the config), and `/status` reports both `quic_blocked` (the choice, which drives the checkbox) and `quic_effective` (what the config actually does). Everything that *can* be derived — the resolver transport, the presence of the rule — is still read back from `config.json` so there is nothing to fall out of sync.
- Fixed: `/set_quic` rebuilt the config with a hardcoded `udp_supported=True`, which re-enabled QUIC on proxies that cannot relay UDP — reintroducing the very handshake hang the automatic block exists to prevent. It now re-probes. It also preserves the resolver transport instead of resetting it to `:53`, which would have killed an nsocks box on a checkbox toggle.
- Fixed: `/self_update` regenerated the sing-box config using the *old* code still resident in memory, so a box on a `:53`-blocked proxy would have stayed broken until the operator pressed Route again. It now regenerates in a subprocess that imports the freshly written file (already proven importable by `validate_new_server_py`), falling back to the old in-process path if the new version lacks those functions. `update.py` gets the same treatment; it already ran after the file swap, so it just needed to call the new probe.
- Fixed: `socks5_connect()` addressed every destination as `ATYP=domain` and read the reply as a fixed 10 bytes. It now uses `ATYP=ipv4` for IP literals — matching what sing-box actually sends once the `resolve` rule has run, so probes exercise the real path — and reads the reply by address type, since a leftover tail corrupts a TLS handshake started on the same socket.
- Fixed: pressing Update in the client failed with "timeout after 30s" while the box was perfectly reachable. Measured on the box with `curl` (5 consecutive runs): DNS was 0.02–5.1 s but `time_connect` was 15.6 / 31.7 / 20.4 / 20.4 / 1.1 s — the timings of kernel SYN retransmission, i.e. the ISP intermittently drops SYNs to GitHub's addresses. The *same* address answers in 1.1 s one moment and 32 s the next, and the box has no global IPv6 at all, so address-family selection was not involved. A single `urlopen(timeout=15)` stalled on the first dead SYN and consumed the client's entire budget. The fix is to make attempts *shorter*, not longer: each retry is a fresh SYN with a fresh chance (and `create_connection` already walks all four of GitHub's A records within one attempt), bounded by an overall deadline so the box returns an honest "GitHub unreachable" well before the client times out. Verified on the box: 0.29–0.33 s in normal conditions, and a clean error at exactly 15.0 s when the host is unreachable. GitHub fetches are additionally pinned to IPv4 as a cheap safeguard for deployments that *do* have a broken IPv6 route — it is a no-op on this box.
- Fixed: right after a push, Update reported "already the latest version" even though the box was demonstrably behind — and once did the opposite, "updating" the box *backwards* onto the previous commit. `raw.githubusercontent.com` serves branch URLs with `cache-control: max-age=300` and keeps returning the previous commit's content for a while after a push; verified on the box that `api.github.com` already reported the new commit while six consecutive branch-URL fetches still returned the old hash, and that a `?cb=…` cache-buster did **not** help. Since the box decides whether to update by comparing its own file against whatever that URL returns, stale content is not merely a delay — it can invert the decision. Fetches now resolve the branch to a commit SHA via `api.github.com` first and then download the SHA-pinned raw URL, which is immutable and always current (verified: correct hash on every attempt, 0.5–0.7 s). If the API is unavailable — including its unauthenticated 60 requests/hour limit — it falls back to the branch URL with a cache-buster, i.e. the previous behaviour.
- Fixed: the client's own update banner had the same stale-CDN flaw, and it bit for real: the banner offered an "update" that was actually the *previous* commit, and clicking it overwrote `client/client.py`, silently reverting a fix that had just been committed. `fetch_github_client_py()` now resolves the branch to a commit SHA via `api.github.com` and downloads the SHA-pinned URL, falling back to the branch URL with a cache-buster if the API is unavailable. Note this check compares raw file content, so a locally modified `client.py` still reads as "update available" — on a development machine, commit before clicking.
- Fixed: `update_client.bat` could never rebuild the exe. `--add-data "client\mag.ico;."` combined with `--specpath client` made PyInstaller resolve the data path relative to the *spec* directory, i.e. `client\client\mag.ico`, so every rebuild failed with `Unable to find … when adding binary and data files`. The script then restored the `.bak` and relaunched the old binary, leaving source and exe silently out of sync — which is why the client update flow appeared to do nothing. It now builds from inside `client/` with paths relative to that directory, and captures the exit code before `popd` (which clobbers `errorlevel`). Verified: build completes with exit 0.
- Fixed: `/self_update` did the config regeneration and both `systemctl restart`s *before* answering, so even a fast fetch could not fit in the client's timeout. It now responds as soon as the new file is written — which is the point at which the update is actually applied — and finishes the rest in the background thread that was already restarting the service, keeping the original order (config → sing-box → service).
- All four deploy scripts copy `server/server.py` verbatim and already create `/var/lib/sing-box`, so every variant (UBUNTU+ROUTER, RASPBERRY+ROUTER, RASPBERRY+WIFI, UBUNTU+WIFI) picks this up with no script changes. Verified: generated configs pass `sing-box check` on v1.13.13, the version `deploy.sh` pins.

## [1.13.0] - 2026-08-09
- Added: self-update for both the Ubuntu server and the Windows client, both pulling from GitHub — no more manually re-copying files to already-deployed boxes.
  - `update.py` (+ `update.bat`/`update.command`) — SSH-based remote updater for an already-deployed box: diffs the box's `server.py` against GitHub, applies with backup + health-check + automatic rollback on failure, regenerates `sing-box` config for whatever proxy is currently active, and creates the `jackal-policy-routing` systemd unit if missing. Supports `--port`/`host:port` (e.g. SSH tunnels), `--type N` for non-interactive/scripted runs, and `--check` for a dry run.
  - `server.py`: `GET /self_update/check` + `POST /self_update` — the box updates itself over HTTP, no SSH needed. Validates the fetched code (compile + import smoke-test in a subprocess) *before* touching the live file, since nothing can roll back a broken version after the process restarts itself.
  - `client.py`: quiet startup check against GitHub; a banner appears only when an update is actually available. Applying it validates via `compile()`, writes the new source, and — since a running `.exe` can't overwrite itself on Windows — hands off to the new `update_client.bat`, which waits for the process to exit, rebuilds with PyInstaller (backup/rollback if the build fails), and relaunches.
- Fixed: `server.py` — SOCKS5 outbound was handing the proxy's destination domain over natively (`ATYP=domain`), letting the *upstream proxy* resolve it on its own backend. For some providers that backend is topologically unrelated to the actual egress node (verified live: real traffic correctly exited via a US residential IP while DNS resolution leaked through a different country). Fixed with an explicit `"action": "resolve"` as the last routing rule, resolving through the same proxy tunnel via IP instead of native domain passthrough. (`domain_strategy` on the outbound does *not* help here — confirmed empirically that it has no effect for protocols with native domain support, contrary to what the field name suggests.)
- Fixed: `server.py` — DNS (`:53`) is now intercepted by TProxy as the *first* rule in the chain, before the private-network `RETURN` rules. Without this, DHCP configurations that hand out the gateway's own IP as DNS (NetworkManager's shared/AP mode) caused DNS queries to match the private-range return and leak outside the proxy entirely.
- Added: `check_udp_associate()` — probes whether the upstream proxy actually supports SOCKS5 UDP ASSOCIATE before applying it. If not, QUIC is now blocked explicitly (`route.rules`) instead of being silently dropped by TProxy — a proxy that can't relay UDP was causing QUIC connection attempts to hang instead of failing fast, which looked like "sites won't load" on Android.
- Added: `/set_quic` + a "Block QUIC" checkbox in the client — lets the operator choose between blocking QUIC (better for antidetect fingerprinting) or allowing it (needed for some apps, e.g. Bet365, that require HTTP/3).
- Added: `/stop_proxy` + a "Stop" button in the client — switches the box to a bypass config (direct traffic, no FakeIP) instead of leaving it in a half-proxied state.
- Fixed: `/set_proxy` and `/stop_proxy` now restart `sing-box`/`jackalrouter` asynchronously in a background thread instead of blocking the HTTP response on the restart, fixing client-side timeouts.
- Backported to all four deploy scripts for consistency: MASQUERADE/FORWARD no longer pinned to the WAN interface name (survives a network/adapter change without reapplying rules), `sing-box` download now retries with `-f` (a failed download used to save the HTML error page as if it were the archive), and policy routing (`fwmark 1 → table 100`) is now backed by a `jackal-policy-routing.service` unit so it survives a reboot.
- Added to `deploy-ubuntu-wifi-ap.sh` / `deploy.sh`: sleep/suspend prevention (`systemd-logind` + masked sleep targets + GNOME power settings) — a laptop acting as the router must keep running with the lid closed.

## [1.12.1] - 2026-07-05
- Reverted: hardware masking (TTL=128, TCP timestamps off, hostname `router`, avahi disabled, MAC spoofing) removed from all three deploy scripts and rolled back on the live Ubuntu box. ## [1.12.0] - 2026-07-05
- Added: network-hardware masking (anti-fingerprint of the box itself) in all three deploy scripts — hides the "Linux laptop" tells from the ISP / proxy provider: outbound **TTL normalized to 128** (Windows-like, vs Linux 64) via `iptables -j TTL`, **TCP timestamps off**, neutral **hostname `router`** (no `family-…` in DHCP/mDNS), **avahi/mDNS disabled**, and **MAC spoofing** of the WAN interface (random, plausible OUI). MAC spoofing is auto-skipped during a remote (`ssh`) deploy since it would drop the link — it's applied only on a local run, with the manual command printed otherwise. Applied and verified live on the Ubuntu box (tcpdump confirmed egress `ttl 128`). Note: this masks the box from the ISP; it does **not** change what target sites see (they see the residential exit node), and it cannot spoof the connected devices' TLS/JA3 fingerprints — that requires an antidetect browser, not a transparent gateway.

## [1.11.2] - 2026-07-05
